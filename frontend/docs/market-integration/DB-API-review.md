# 상권 지도 통합 — DB·API 2차 검토

## 결론

**현재 DB를 전면 재설계할 필요는 없다.** 지도 화면 통합은 공용 정적 인구·도로 자산과 기존 가게 데이터로 진행할 수 있다. 백엔드 연결 시에는 가게 주소의 좌표 계약, 데이터 버전, 반경·필터별 응답과 캐시 키를 먼저 확정한다. 사용자별 지도 설정의 서버 저장, 데이터 버전 카탈로그, 격자 단위 분석 테이블은 요구가 생길 때 추가한다.

이번 DB 검토에서는 원격 DB에 다시 접속하지 않았고 DDL·migration·데이터 변경을 실행하지 않았다. 기준은 [제공받은 스키마 원문](DB-schema-current.md)과 **2026-11-20 20:01 KST**의 이전 읽기 전용 스냅샷이다. 당시 업무 테이블 10개·131개 컬럼과 문서의 이름·타입·NULL 허용 여부가 일치했다. 현재 스키마 원문 SHA-256도 직전 검토와 같다(`ee958ef1be28646965a7a65aab2674c1c1c075ea7e3a7475a008a5e78f6e84dc`). 현재 서버가 이후 변경되지 않았다고 확인한 것은 아니다.

### 반드시 유지할 데이터 의미

- **도로 색은 그 위치의 250m 생활인구를 표현한다. 도로별 실측 보행량·유동량이 아니다.** 동일 격자의 여러 도로는 같은 격자 값을 공유하며 도로 조각별 값을 더하면 중복 집계된다.
- `number`는 공개값 합계, `[sum, observedCount, suppressedCount]`는 일부 비식별, `"*"`는 전부 비식별, `null`/원본 행 없음은 미제공이다. 공개된 `0`을 비식별·미제공과 구분한다.
- 비식별 튜플의 count는 총계 파일에서는 원본 행 수, 성별·연령 파일에서는 세부 열의 공개/비식별 개수를 누적한다. 이를 인구 수나 동일 단위의 행 수로 해석하지 않는다.
- 성별·연령은 **내국인만**의 분류다. `local + male + female`, `local + 모든 연령`처럼 총계와 세부집단을 함께 더하지 않는다.
- 반경 합계는 격자 중심점이 반경 안에 들어오는 격자들의 공개값 합계다. 경계에 걸친 면적 비례 보정이나 도로 길이 가중치가 아니다.
- 단계는 250m 격자당 1,000 / 2,000 / 4,000명 경계의 서비스 공통 인원 기준이다. 집단·시간·위치·반경에 따라 재계산하지 않는다. 공식 위험도·경쟁도 등급이 아니다. 도로 연결부의 색상 보간은 시각 표현이며 툴팁·등급·합계는 원래 격자 공개값을 사용한다.
- 원본 평균 함수는 전부 비식별인 시간도 분모에 넣어 주석과 계산이 달랐다. 통합 수정의 계약은 **공개값이 있는 시간의 평균**이다. 관측시간 수를 같이 표시하고, 반경 합은 ‘격자별 공개시간 평균의 합’으로 설명한다. 24시간 체류 인원이나 일일 순방문자로 표시하지 않는다.

## MVP에서 재사용할 DB

| 요구 | 기존 구조 | 보완 계약 |
|---|---|---|
| 가게 기준 좌표 | `stores.address_codes` 설명에 이미 `coord:{lat,lng}` 포함 | WGS84 숫자, 위도/경도 범위, geocode 성공/실패, 원본 주소와 좌표의 버전을 검증한다. 좌표가 없는데 0,0을 채우지 않는다 |
| 탐색 중심·반경·집단·시간 | DB 필수 아님 | 화면 상태로 유지한다. 가게 좌표와 별개다. ‘이 위치를 내 가게로 저장’ 같은 명시적 기능 전에는 가게 레코드를 수정하지 않는다 |

| 인구·도로 원본 | 공용 정적 자산 | 가게별 JSONB에 전체 30MB를 복제하지 않는다. 같은 불변 버전 URL을 공유한다 |
| 기준일·출처·품질·집계 버전 | manifest 파일로 시작 가능 | `populationDate`, `boundaryVersion`, `roadsVersion`, `aggregationVersion`, 해시, 라이선스·출처·품질 정보를 묶는다 |
| 목표 가격 입력 | 현재 계정별 localStorage `myprice` | 현재처럼 로컬 유지 가능. 기기 간 동기화가 필요할 때 가게별 가격 설정으로 저장한다. 주변 실측 가격 데이터와 분리한다 |
| 예시 점포/가격 | (2026-11-22 제거됨: `SHOPS`·`EXFOOD`·`PRICE_EX`. 주변 점포는 카카오 실제 조회, 가격 비교는 제외) 당시 `SHOPS`, `EXFOOD`, `PRICE_EX` | API 실데이터로 표시하거나 DB에 검증된 사실처럼 적재하지 않는다. 응답에 `mode: demo`와 실제 수집 범위를 제공한다 |

`jsonb`는 JSON 문법과 저장 형식을 제공하지만 `coord`, `options` 같은 내부 업무 스키마까지 자동 검증하지 않는다. 좌표/집단/시간 검증은 API DTO에서 명시하고 필요한 제약만 DB에 둔다. [PostgreSQL JSON 문서](https://www.postgresql.org/docs/18/datatype-json.html)

### 좌표 변경과 캐시

주소 변경 → 기존 주소 좌표 무효화 → 새 geocode 성공 시 원본 주소 버전과 함께 교체한다. 실패 시 이전 주소의 좌표를 새 주소에 붙이지 않는다. 응답에는 `centerSource: store | map-selection | demo-fallback`을 구분한다. 최종 UI의 필드명은 구현 타입에 맞춰 adapter에서 정한다.

캐시 키는 canonical request의 해시로 만든다. 인구 계산은 `releaseId + aggregationVersion + center(lat,lng) + radiusM + category + group + hour(KST)`를 포함한다. 점포 조회는 공급자·업종·중심·반경·페이지/조회 범위를 포함한다. 좌표를 반올림해 재사용한다면 반올림 규칙과 실제 계산 중심을 응답에도 노출한다. 인증 사용자 데이터가 섞인 결과는 공용 캐시에 넣지 않으며 `storeId` 요청은 항상 로그인 계정 소유 여부를 확인한다.

새 공개 데이터 버전은 새 URL/키로 배포하고 manifest를 원자적으로 교체한다. `populationDate`가 다른 파일을 ‘전체’로 합치지 않는다. 기존 build-grid는 중복키/기준일 불일치를 기록하거나 경고한 뒤 출력할 수 있으므로, 운영 배치에는 이를 게시 중단 조건으로 두는 것이 필요하다. 현재 제공 묶음에는 기준일 불일치·중복키가 없다.

## 권장 API 계약 초안

**아래는 제안이며 현재 서버에 구현되었다고 확인한 endpoint가 아니다.** 정적 파일 기반 MVP에서는 1번 manifest와 3번 응답의 계산 모델을 프론트 loader에서 공급해도 된다.

| API 후보 | 주요 응답/동작 |
|---|---|
| `GET /api/market/datasets/current` | releaseId, 인구 기준일, 13개 자산 URL, 도로 index URL, 경계/도로/집계 버전, 출처·품질, 지원 집단 목록 |
| `GET /api/stores/{storeId}/market/context` | 인증된 가게 주소와 검증된 좌표, 좌표 상태/주소 revision, 기본 탐색 반경. 선택한 지도 중심과 분리 |
| `GET /api/market/population?releaseId=…&lat=…&lng=…&radiusM=…&category=…&group=…&hour=…` | 선택 조건 그대로, covered/no_data 구분, 공개 격자 수·비식별 격자 수, 공개 합계/평균 방식, 공통 인원 경계와 표시 기준 버전. 서버 계산으로 전환할 때 도입 |
| `GET /api/market/places?lat=…&lng=…&radiusM=…&category=…` | 공급자 ID·좌표·거리·업종·출처·시점·demo/live 구분, 조회 완전성·pagination. 전체 개수와 받아온 목록 길이 구분 |
| `GET /api/market/prices?…` | 동일 품목·사이즈·온도·통화/관측일·표본수·출처가 확보된 경우에만 분포 제공. 현재 예시 범위는 `mode=demo` |
| `PUT /api/stores/{storeId}/market/preferences` | 기기 간 동기화 요구가 있을 때만. 탐색 좌표·반경·필터·목표 가격 저장, 가게 주소 변경 아님 |

필수 검증: 유한한 WGS84 좌표, 반경 250–2,000m(현재 UI는 250m 간격), KST 시간 0–23 또는 avg, type→all/local/fornLong/fornTemp, sex→male/female, age→a00…a70. 서울 밖 또는 공개 행 없는 범위는 `no_data`로 반환하며 ‘실제 인구 0명’으로 변환하지 않는다. 일부만 비식별인 합계에는 `partial` 표시가 필요하다.

권장 집계 DTO의 의미는 [필드 매핑표](market-field-mapping.csv)에 정리했다. 평균값은 단순 `totalPopulation`보다 `value`와 `metric: public_hourly_sum | sum_of_cell_observed_hour_means`를 함께 쓰는 편이 안전하다. `gridCount`도 제공행이 있는 수·공개값 있는 수·비식별만 있는 수를 구분하면 0·미제공 혼동을 막을 수 있다.

## 필요한 경우에만 추가할 테이블

[선택 확장 DDL 초안](optional-market-schema.sql)은 **실행되지 않았고 Alembic migration도 아니다.** 다음 두 요구가 확정될 때 사용하는 예시다.

1. `market_data_releases`: 운영자가 여러 배포 버전을 관리할 때 공용 manifest·해시·기준일·집계 버전·품질만 저장한다. 인구/도로 본문은 공용 자산 저장소에 둔다.
2. `store_market_preferences`: 지도 조건과 목표 가격을 계정/기기 간 동기화할 때 가게당 1행으로 저장한다. `stores` FK로 귀속하고 사용자의 소유권 검증은 서버에서 수행한다.

JSON 품질·manifest의 내부 검증은 별도 schema가 필요하다. CHECK는 행 내부 값 검증, 관계·소속은 FK로 보장한다. [PostgreSQL 제약 문서](https://www.postgresql.org/docs/18/ddl-constraints.html)

일자별 장기 추이·서버 공간 질의가 실제 요구되면 별도 분석 저장소에 `grid(boundary_version, cell_id, geometry)`와 `population_observation(dataset_version, date, hour, population_type, group, cell_id, public_value, disclosure_state)` 등을 검토한다. 원본 키의 행정동을 유지한 raw 층과 집계 층을 구분하고, 수치 없는 비식별과 원본 행 없음을 보존한다. 지금 화면 통합만으로 PostGIS·전체 사실 테이블·도로별 인구 테이블을 필수로 도입할 이유는 없다.

## 이전 검토에서 여전히 남은 항목

- **R1 참조 무결성:** report_items/cost_logs의 store_id와 run_id 독립 FK 문제는 제공 스키마에 그대로다. 가게가 다른 run을 연결하지 못하게 하는 보완 필요.
- **R2 지원사업 일정:** grant의 절대 마감과 개업일 상대 task를 구분해야 한다. 최신 코드도 grant를 별도 캘린더 이벤트로 합성하므로 서버 g-* 도입 시 중복 방지 필요.
- **R3 오래된 분석 결과:** 입력 변경·분석 완료 순서와 사라진 선택지 효과 초기화 정책은 서버 코드 미제공으로 미확인이다.
- **R4 비용 로그:** 발생 시각 없음·run/store 모두 nullable 문제는 동일 스키마에 남아 있다.
- **R5 자금 0: 수정 완료.** 입력 초안·변경 비교·저장·0원 표시에서 빈 값과 0을 구분했다. 브라우저 회귀 검사에서 추가 발견한 nullable 저장값이 시연 기본값으로 돌아오는 복원 문제도 함께 수정했다. 폼에서 0과 빈 값을 각각 저장하고 새로고침 후 0/null과 입력 표시가 유지되는 것을 검증했다.
- **R6 메뉴:** 현재 타입·UI·분석 생성에서 제거되어 저장 컬럼 추가 대상으로 보지 않는다.
- **R7 DTO:** grant checks 객체↔tuple, summary/null, recommendation, action 필드 변환은 계속 필요하다. UI 경로 변경에 맞춰 알림 CTA도 최신 route/docs/widget 동작으로 검증한다.

## 검증·인수 조건

- 주소 변경 후 지오코딩 실패/늦은 응답이 이전 좌표를 새 주소의 위치로 덮어쓰지 않는다.
- 지도 클릭·반경 변경으로 같은 중심/반경 기준의 인구와 점포 목록을 계산한다. 예시 범위 밖에서 실제 점포가 없다고 단정하지 않는다.
- 공개0, 전부비식별, 일부비식별, 행없음 fixture가 서로 다른 표시·집계 결과를 낸다.
- `[100, "*", null]`의 공개시간 평균은 100이며 관측시간은 1이다. 비식별 시간은 0인 관측시간으로 세지 않는다.
- 전체/성별/연령 빠른 전환에서 이전 요청 결과가 최신 필터를 덮어쓰지 않는다.
- 기준일/버전이 섞인 파일, 중복 원본키, 잘못된 값은 배포 전에 검출한다. 조인 누락 목록과 공개 합계 검증을 보존한다.
- SDK 실패·데이터 로딩 실패·서울 밖·0 공개값 상태를 구분한다.
- 소유하지 않은 storeId의 context/preferences 접근 거절, 공용 데이터/캐시와 개인 설정 분리.

후속 서버 검토에는 전체 `docs/DB 명세서.md`, 모델·Alembic 리비전, API DTO, 규칙 YAML, geocode/외부조회/분석 완료 처리 코드가 필요하다. 이번에는 로컬 프론트·지도 소스와 스키마 요약본 기준으로만 판단했다.
